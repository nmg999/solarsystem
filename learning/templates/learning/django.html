What does Django do?

Django is a Python framework for building websites. A framework provides useful tools and a structure so you do not have to build everything from scratch. Django runs on a server, the computer that responds to requests from your browser.

In this project, config holds the site settings and learning is the app containing your study pages. A URL route matches an address, a view is the Python function that handles the request, and a template supplies the HTML for a page.

When you open /science/, Django finds its route, calls the Science view, and renders the Science Study template. Your browser displays the result.

What does HTML do?

HTML defines the content and structure of a web page. It stands for HyperText Markup Language. Tags describe headings, paragraphs, links, images, forms, and other page elements.

<h1>Study Hub</h1>
<p>Choose a subject to explore.</p>
<a href="/science/">Science</a>

<h1> marks a main heading, <p> marks a paragraph, and <a> creates a link. The link's href tells the browser where to go.

Your Study Hub templates use HTML for the subject cards. Your solar system uses an HTML <canvas> element as a drawing surface for the planets.

What does CSS do?

CSS controls how a page looks and how its elements are arranged. It stands for Cascading Style Sheets. CSS sets colours, fonts, spacing, borders, and layouts, including layouts that adapt to phone screens.

h1 {
  color: blue;
  font-size: 40px;
}

This rule selects h1 headings and makes their text blue and 40 pixels tall.

Study Hub's shared base.html template includes CSS that styles the cards and green buttons. In your solar system, CSS styles the information panels, controls, and quiz.

What does JavaScript do?

JavaScript adds behaviour and interactivity. In your website it runs in the browser, responds to clicks and other events, changes page content, and draws animations.

<button id="greet">Say hello</button>
<p id="message"></p>
<script>
  document.getElementById('greet').addEventListener('click', () => {
    document.getElementById('message').textContent = 'Hello, explorer!';
  });
</script>

This example finds the button, listens for a click, and then changes the paragraph's text.

In solar_system.html, JavaScript draws the detailed planets, animates their orbits, displays planet facts, scores your quiz, and controls time travel and cinematic effects.

What is a database?

A database stores information so an application can retrieve, change, or delete it later. In a relational database, information is organised into tables with rows and columns. Each row is a record, such as one learner or one quiz attempt.

Django can describe stored data using Python classes called models. Commands called migrations create or update the corresponding database structure.

Your project uses SQLite, which stores its database in db.sqlite3. A future quiz-results table could store a learner, their score, and when they took the quiz.

Your current solar system quiz calculates scores in the browser. It does not save quiz attempts to the database, so reloading the page clears that result.

What is an API?

An API is an agreed way for software to communicate. It stands for Application Programming Interface. An API describes the operations a program can use and the information it receives back.

A web API lets a program send a request to an address, called an endpoint, and receive data. That data often uses JSON, a text format for named values and lists.

GET /api/planets/mars/

Example JSON response:
{
  "name": "Mars",
  "nickname": "The red planet",
  "orbital_period_earth_days": 687
}

This is an imagined endpoint, not one currently built into your site. In a future version, JavaScript could request planet information from a Django API and display the response without reloading the page. Your current planet information is embedded in the solar system file.

Not every API uses the internet: your JavaScript also uses the browser's Canvas API to draw planets and effects.

What does models.py do?

models.py describes the information your app stores in its database. A model is a Python class representing a type of record. Its fields describe the pieces of information to store, such as a planet's name or a quiz score.

from django.db import models

class Planet(models.Model):
    name = models.CharField(max_length=100)
    orbital_period_days = models.FloatField()

In this example, Planet describes planet records. CharField stores text and FloatField stores a number that can include decimals. Django can use this class to create, find, update, and delete records without you writing database queries by hand.

Your learning/models.py currently has no custom models. This Planet model is an example, not a model already added to your project. Your planet facts currently live in solar_system.html.

After adding or changing a model, you normally run python manage.py makemigrations to describe the database changes, then python manage.py migrate to apply them.

What does views.py do?

views.py contains the Python code that handles requests and returns responses. A request is what your browser asks for; a response is what Django sends back. A view can read database records, process submitted information, and choose a template to display.

from django.shortcuts import render

def science(request):
    return render(request, 'learning/science.html')

This is the Science view in your project. request contains information about the incoming request. render uses the HTML template to build a response for the browser.

Your learning/views.py has views for Study Hub, Science Study, and Django Study. Its solar_system view returns the existing solar system HTML file with FileResponse, which sends a file as the response.

What does urls.py do?

urls.py connects website addresses to views. Each URL pattern is a route. Django checks the routes to find the view that should handle an incoming address.

from django.urls import path
from . import views

urlpatterns = [
    path('science/', views.science, name='science'),
]

This route connects /science/ to the science function in views.py. The name science lets Django build links to the route without repeating its address throughout your templates.

Your config/urls.py is the main routing file. It uses include to pass Study Hub's routes to learning/urls.py, where the home, Science, solar system, and Django Study addresses are defined.

Follow a request: opening /science/ matches a route in urls.py, calls the function in views.py, and returns the Science HTML template. A view can also use models from models.py when it needs stored data.

What does .venv do?

.venv is a virtual environment: a folder that keeps this project's Python setup and installed packages separate from other projects. Different projects can use different package versions without interfering with each other.

In this repository, .venv uses Python 3.14.10 and contains Django. Activating the environment makes commands such as python and pip use this project's environment in your current terminal.

# Activate in Windows PowerShell:
.\.venv\Scripts\Activate.ps1

# Check Django after activation:
python -m django --version

# Leave the environment:
deactivate

If PowerShell blocks activation scripts, run Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass first. That setting lasts only for the current PowerShell session.

You can also use the environment directly without activating it: .\.venv\Scripts\python.exe manage.py runserver 8080. Each developer normally creates their own environment rather than uploading the .venv folder to GitHub.

What does .gitignore do?

.gitignore tells Git which untracked files and folders to leave out of version control. Git tracks changes to your project; GitHub hosts the commits you push. Ignoring generated or computer-specific files keeps unnecessary files out of those commits.

.venv/
__pycache__/
*.py[cod]
db.sqlite3

These entries are in your repository. They ignore the virtual environment, Python cache folders and compiled files, and the local SQLite database. A trailing slash marks a folder; * matches a pattern.

Your source files, templates, and requirements.txt can be committed while your local packages and database stay on your computer.

Adding a file to .gitignore does not delete it or stop tracking it if it was already committed. It also does not remove information from earlier commits or encrypt private data.

What does requirements.txt do?

requirements.txt lists Python packages to install for the project. It helps another developer or your hosting service install the dependencies your code needs.

Django==5.2.19

This is the current entry in your file. == pins an exact version, so this requirement installs Django 5.2.19 rather than choosing a different release.

# Install the listed packages into this project's environment:
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

The -r option tells pip, Python's package installer, to read the package list from the file. Django's own dependencies are installed automatically; this file currently pins only Django, not every dependency.

Together, these three pieces make setup repeatable: commit requirements.txt, ignore .venv/, and install the listed packages inside a new virtual environment on each computer. The requirements file lists packages; it does not install Python itself.

What does manage.py do?

manage.py lets you run Django commands for this project from your terminal. It tells Django which settings module to use, then passes your command to Django's command-line tools.

# Start the local development server:
.\.venv\Scripts\python.exe manage.py runserver 8080

# Check the project for common configuration problems:
.\.venv\Scripts\python.exe manage.py check

# Apply database migrations:
.\.venv\Scripts\python.exe manage.py migrate

Your manage.py points Django to config.settings. Run these commands from the repository folder containing manage.py. You normally use this file as generated rather than adding your page code to it.

What's the difference between urls.py in the project folder and urls.py in the app folder?

The project's URL file organises routes for the whole website. The app's URL file organises routes belonging to that app. Splitting them keeps related pages together and makes it easier to add more apps later.

# config/urls.py — project routing:
from django.urls import include, path

urlpatterns = [
    path('', include('learning.urls')),
]

# learning/urls.py — app routing:
from django.urls import path
from . import views

urlpatterns = [
    path('science/', views.science, name='science'),
]

These excerpts show how your study routes connect. Your complete project URL file also includes the admin route. The empty prefix '' passes matching addresses to learning.urls without adding another path segment, so the Science address is /science/.

If the project used path('study/', include('learning.urls')) instead, that app's Science address would become /study/science/. Django removes the matched project prefix before checking the app's patterns. An app URL file is a useful convention, not a requirement for every Django app.

Why do we see __init__.py in many folders?

__init__.py marks a folder as a regular Python package. A package groups related Python modules, which are usually individual .py files, so other code can import them.

Your config/__init__.py makes config a regular package, and learning/__init__.py does the same for the app. The file in learning/migrations/ makes that folder a regular package too. They can be empty and still do their job.

Python executes a package's __init__.py when it first imports that package in a process. You usually leave these generated files empty unless the package needs setup code. Some Python packages, called namespace packages, can work without this file, so not every folder needs one.

What does settings.py do?

settings.py configures how your Django project runs. Your file is config/settings.py. It contains Python values that Django reads to decide which apps, databases, templates, and other services to use.

INSTALLED_APPS registers apps such as learning. DATABASES chooses the database, currently SQLite in your local project. TEMPLATES controls where Django looks for HTML templates, and ROOT_URLCONF selects the main URL module.

ALLOWED_HOSTS lists hostnames Django accepts. DEBUG controls detailed development error pages. SECRET_KEY is used for cryptographic signing, such as signing session data; it is not your database password.

Your settings register learning so Django can find its templates. They also allow your local and configured Vercel hostnames. Production settings should disable debug pages and use a stable, private secret key supplied through the hosting environment.

What does the migrations folder in the app folder do?

The migrations folder stores a versioned history of changes to your app's database structure. Migration files describe operations such as creating a table or adding a field. Some migrations also change stored data.

# Create migration files from model changes:
.\.venv\Scripts\python.exe manage.py makemigrations

# Apply pending migrations to the configured database:
.\.venv\Scripts\python.exe manage.py migrate

# See which migrations have been applied:
.\.venv\Scripts\python.exe manage.py showmigrations

makemigrations compares your models with the state recorded in migration files; it does not directly compare them with your live database. migrate then applies the required changes and records which migrations have run.

Your learning/migrations/ currently contains only __init__.py because the app has no custom models yet. Django's built-in apps have their own migrations, which created tables for features such as users and sessions when you ran migrate.

Migration files should normally be committed to Git so other computers and deployments can apply the same changes. They describe changes; they are not database backups. Avoid deleting applied migrations just to clear an error.

How they work together

Your browser requests a page. Django handles the request and can read information from a database. It sends back HTML, which the browser displays with CSS styling. JavaScript then responds to your actions and can request more data through a web API.
